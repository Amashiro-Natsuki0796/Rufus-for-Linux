# 第 6 章　扩展功能实现（冲突进程检测 / 在线下载 / UEFI:NTFS）

> 本章记录 1.1.0 版补齐的三项上游能力。它们原本被列为"未移植"，
> 现按上游语义在 Linux 上完整实现。

## 6.1　冲突进程检测

### 6.1.1　上游做法

上游 `src/process.c` 的 `SearchProcessThread()` 是一个常驻后台线程：

1. `NtQuerySystemInformation(SystemExtendedHandleInformation)` 枚举**全系统句柄**；
2. 用 `NtDuplicateObject` 把每个句柄复制到自身进程；
3. `GetFileType(dupHandle) != FILE_TYPE_DISK` 的丢弃（避免 `NtQueryObject` 卡死）；
4. `NtQueryObject(ObjectNameInformation)` 取对象名；
5. 与 `SetProcessSearch(DeviceNum)` 预先算好的目标字符串比对——
   物理盘设备路径（`\Device\HarddiskN\DRN`）**加上所有盘符的 DOS 设备名**；
6. 命中后取回进程命令行与 `GrantedAccess` 权限掩码，填入 `blocking_process` 结构。

`rufus.c` 在用户点"开始"后调用 `StartProcessSearch()`，并在检测到占用时
提示用户关闭相关程序。

### 6.1.2　Linux 等价实现

Linux 没有"枚举全系统句柄"的接口，但 `/proc` 提供了更直接的等价信息。
`src/core/rf_process.c` 的做法：

```
上游                                       本移植
---------------------------------------    ----------------------------------------
NtQuerySystemInformation(句柄表)           遍历 /proc/<pid>/
NtQueryObject(ObjectNameInformation)       readlink("/proc/<pid>/fd/N")
与 \Device\HarddiskVolumeN 比对            与设备节点及挂载点前缀比对
GetProcessCommandLine                      /proc/<pid>/cmdline
GetModuleFileNameEx / QueryFullProcess...  readlink("/proc/<pid>/exe")
句柄 GrantedAccess 掩码                     /proc/<pid>/fdinfo/N 的 flags 字段
（无对应）                                  /proc/<pid>/cwd、/proc/<pid>/root
（无对应）                                  /proc/swaps（交换分区占用）
```

**目标路径集合**（`rf_process_target_paths()`）：
设备节点本身 + 所有分区节点 + 所有挂载点。

**判定的占用方式**（`rf_hold_kind`）：

| 枚举 | 含义 | 判定来源 |
| --- | --- | --- |
| `RF_HOLD_BLOCKDEV` | 直接打开了块设备 | `fd` 目标以 `/dev/` 开头 |
| `RF_HOLD_MOUNT` | 打开了挂载点下的文件 | `fd` 目标在挂载点前缀下 |
| `RF_HOLD_CWD` | 工作目录位于挂载点下 | `/proc/pid/cwd` |
| `RF_HOLD_EXE` | 可执行文件位于挂载点下 | `/proc/pid/exe` |
| `RF_HOLD_SWAP` | 被用作交换空间 | `/proc/swaps` |

访问模式从 `/proc/pid/fdinfo/N` 的 `flags` 字段按 `O_ACCMODE` 解析为
"只读 / 只写 / 读写"。

### 6.1.3　集成策略

上游是"持续监测 + 提示"，本移植改为**破坏性操作前扫描一次**——
这更符合 Linux 的 CLI/脚本使用方式，也避免常驻线程。

`rf_create_bootable_usb()` 在第 2.5 步（校验目标之后、卸载之前）执行：

- **无占用** → 继续；
- **仅"已挂载"造成** → 自动卸载后继续（这是可自行解决的冲突）；
- **其他占用**（文件管理器、同步工具、`dd` 等）→ **拒绝执行**并列出进程，
  提示用户关闭；`--no-conflict-check` 可强制继续，`--force` 亦会放行但给出警告。

> 实测证明这一拦截是必要的：用 `--no-conflict-check` 强行在一个已挂载的
> NTFS 分区上创建启动盘时，`cp` 确实报 `Input/output error` 而失败
> （见第 5 章测试 14）。

### 6.1.4　命令

```bash
rufus ps /dev/sdb          # 列出占用者
rufus ps --json /dev/sdb   # 机器可读输出
```

退出码：`0` 无占用，`2` 有占用。

## 6.2　在线下载 ISO

### 6.2.1　上游做法与移植取舍

上游 `net.c` 的 `DownloadISO()` **并不自己维护镜像列表**，而是：

1. 从 `fido_url` 下载 [Fido](https://github.com/pbatard/Fido) 脚本（压缩 + RSA 签名校验）；
2. 用 `bled`（内嵌 LZMA）解压；
3. 把脚本写到临时目录并**用 PowerShell 执行**；
4. Fido 弹出官方 ISO 列表，用户选择后由 Rufus 的 `DownloadToFileOrBufferEx()` 下载。

Fido 是 PowerShell 脚本，在 Linux 上没有对应物。因此移植版把这一层
**改为自带的 JSON 目录 + 原生 HTTP 下载器**，这是结构上的等价替换：

| 上游 | 本移植 |
| --- | --- |
| Fido PowerShell 脚本（远程，签名校验） | 内置 `iso-catalog.json`（可远程更新） |
| WinHTTP / WinINet | libcurl（缺失时回退 `curl`/`wget` 命令行） |
| RSA 签名校验脚本 | 下载后按官方 SHA256 校验和验证镜像本体 |

### 6.2.2　HTTP 层

`src/core/rf_http.c` 提供统一接口，编译期自动选择后端：

```
pkg-config --exists libcurl  →  RF_HAVE_LIBCURL  →  libcurl 后端
否则                          →  curl / wget 命令行后端
```

libcurl 后端提供：进度回调、断点续传（`CURLOPT_RESUME_FROM_LARGE`，
写入 `.part` 临时文件，成功才 `rename`）、重定向跟随、代理、TLS 校验、
低速超时。命令行后端为降级方案，仅报告开始/结束。

> `debian/control` 中 `libcurl4t64` 由 `dh_shlibdeps` 自动加入 `Depends`。

### 6.2.3　目录格式

```json
{
  "catalog_version": "2026.10",
  "updated": "2026-10-13",
  "entries": [
    {
      "id": "ubuntu-2404-desktop-amd64",
      "name": "Ubuntu 24.04 LTS Desktop",
      "version": "24.04.5.1",
      "arch": "x86_64",
      "url": "https://releases.ubuntu.com/24.04/ubuntu-24.04.5.1-desktop-amd64.iso",
      "sha256_url": "https://releases.ubuntu.com/24.04/SHA256SUMS",
      "sha256": "4da4a0c9...",
      "size_bytes": 6250332160,
      "category": "linux",
      "type": "iso",
      "homepage": "https://ubuntu.com/download/desktop"
    }
  ]
}
```

内置目录含 **53 个条目**（Windows 5、Linux 40、BSD 3、工具盘 5），
所有 URL 均实测可访问，`size_bytes` 与服务器 `Content-Length` 一致。

查找顺序：用户目录 → 系统目录 → 构建树

```
~/.config/rufus-linux/iso-catalog.json      ← --update-catalog 写入这里
/usr/share/rufus-linux/iso-catalog.json     ← 随包安装
<可执行文件目录>/data/iso-catalog.json      ← 构建树
```

用一个 250 行的极简 JSON 解析器（`src/core/rf_json.c`）读取，避免引入
JSON 库依赖。

### 6.2.4　校验和解析

`rf_checksum_parse()` 支持主流发行版的校验和文件格式：

| 格式 | 示例 | 覆盖的发行版 |
| --- | --- | --- |
| coreutils 双列 | `<hash>  <file>` | Debian、Arch、Clonezilla |
| coreutils 二进制标记 | `<hash> *<file>` | Ubuntu、SystemRescue |
| BSD 风格 | `SHA256 (file) = <hash>` | Fedora、Rocky、AlmaLinux、FreeBSD、OpenBSD |
| 单文件裸 hash | `<hash>` | Manjaro、openSUSE、Raspberry Pi OS |
| 带路径前缀 | `<hash>  v8.10/<file>` | Memtest86+ |

对 PGP clearsigned 的 CHECKSUM（Fedora / AlmaLinux）无需特殊处理——
签名头尾行不含 64 位十六进制，自然被跳过。

**校验流程**：优先用目录内嵌 `sha256`；否则下载 `sha256_url` 并解析；
两者都拿不到时给出明确警告而不是静默通过。

> 注意实践中的两个陷阱（都已处理）：
> 1. URL 取文件名必须取**最后一段**——`.../v8.10/xxx.iso.zip` 应得到
>    `xxx.iso.zip`，否则无法与官方校验和文件中的条目对上；
> 2. `rf_hash_hex()` 的第二个参数是**摘要字节数**而非算法枚举，
>    传错会只打印前几个字符。

### 6.2.5　命令

```bash
rufus download --list                  # 列出全部 53 条
rufus download --list ubuntu           # 按关键字过滤
rufus download ubuntu-2404-desktop-amd64 --dir ~/ISO
rufus download --url https://.../x.iso # 直接下载任意 URL
rufus download --update-catalog <URL>  # 更新目录到 ~/.config/rufus-linux/
rufus download --catalog <文件> <ID>   # 使用指定目录
rufus download --no-verify <ID>        # 跳过校验（不推荐）
```

GUI 中"引导选择"右侧的 **下载 ISO** 按钮打开可搜索的列表对话框。

## 6.3　UEFI:NTFS

### 6.3.1　背景

UEFI 固件只能从 FAT 分区读取引导器。当 Windows 安装盘的
`sources/install.wim` 超过 4 GiB 时，必须使用 NTFS 或 exFAT（FAT32 单文件上限），
但此时固件无法直接读取该分区。

解决办法（[pbatard/uefi-ntfs](https://github.com/pbatard/uefi-ntfs)）：
在盘尾放一个**小 FAT 分区**，里面装一个 UEFI 驱动：

```
固件 → 读 FAT 分区的 EFI/Boot/bootx64.efi（UEFI:NTFS 驱动）
     → 驱动挂载 NTFS 分区
     → 加载 NTFS 上的 EFI/Microsoft/Boot/bootmgfw.efi
```

### 6.3.2　上游做法

上游把驱动镜像 `res/uefi/uefi-ntfs.img`（1 MiB FAT12）作为 **Windows 资源**
`IDR_UEFI_NTFS`（资源号 502）内嵌，然后在 `drive.c` 中：

- `format.c` 判定 `extra_partitions |= XP_UEFI_NTFS`，条件为
  「镜像可 UEFI 引导 **且** 文件系统为 NTFS/exFAT」或用户显式选择 `BT_UEFI_NTFS`；
- 分区大小 `CEILING_ALIGN(uefi_ntfs_size, bytes_per_track)`，
  位置在**磁盘末尾**（`drive.c` 从后往前分配偏移）；
- 写分区表后，把镜像**原样写入**该分区起始偏移（不格式化）。

> 该镜像就在上游源码树中，因此本移植**直接复用它**——
> 与 libcdio、ms-sys 一样属于"原样搬入"。

### 6.3.3　分区属性（与上游逐条一致）

| 属性 | 值 | 上游原因 |
| --- | --- | --- |
| 分区名 | `UEFI:NTFS` | 与上游同名，便于识别 |
| MBR 类型字节 | `0xEF` | EFI System Partition |
| GPT 类型 GUID | `EBD0A0A2-B9E5-4433-87C0-68B6B72699C7`（MS Basic Data） | **故意不用 ESP GUID**：Windows 安装程序看到两块 ESP 会在"复制 Windows 文件"阶段报错 |
| GPT 属性 | bit 63（不分配盘符） | 避免占用盘符 |
| 内容 | 原始 `uefi-ntfs.img` | 不格式化，镜像本身就是完整 FAT 文件系统 |

### 6.3.4　布局计算

`rf_uefi_ntfs_layout()` 的实现：

```
GPT:  last_usable = total_sectors - 34        （备份项 32 + 备份头 1 + 主头 1）
MBR:  last_usable = total_sectors - 1

uefi_sectors = align_up(ceil(img_size / sector_size), 1 MiB)
uefi_start   = align_down(last_usable + 1 - uefi_sectors, 1 MiB)
main_sectors = uefi_start - main_start_lba      （main_start_lba = 2048）
```

上游用 `bytes_per_track`（63×512）对齐，本移植用更规整的 1 MiB——
两者都是合法的，1 MiB 与现代分区工具的习惯一致（`sgdisk` 校验通过）。

### 6.3.5　镜像查找

`rf_uefi_ntfs_image_path()` 依次尝试：

1. `--uefi-ntfs=<路径>` 命令行覆盖；
2. 环境变量 `RUFUS_UEFI_NTFS_IMG`；
3. `/usr/share/rufus-linux/uefi-ntfs.img`（随包安装）；
4. `/usr/local/share/rufus-linux/uefi-ntfs.img`；
5. 可执行文件同级的 `data/uefi/uefi-ntfs.img`（构建树）。

镜像大小必须在 256 KiB – 16 MiB 之间，否则视为损坏。

### 6.3.6　命令

```bash
rufus uefi-ntfs                                     # 显示镜像状态与分区属性
sudo rufus create --fs ntfs win11.iso /dev/sdb      # 自动启用（镜像可 UEFI 引导时）
sudo rufus create --fs ntfs --uefi-ntfs win11.iso /dev/sdb   # 强制启用
sudo rufus create --fs ntfs --uefi-ntfs=/path/uefi-ntfs.img ...
```

GUI 中为 **UEFI:NTFS 分区** 复选框。

## 6.4　顺带修复的两个既有缺陷

补齐这三项功能的过程中，暴露出 1.0.0 版中两个**真实缺陷**，一并修复：

### 6.4.1　`rf_part_write()` 的栈缓冲区溢出

```c
/* 修复前 */
if (!sig) {
    unsigned char r[4];
    gen_guid(r);        /* gen_guid 写入 16 字节 → 越界 12 字节 */
    memcpy(&sig, r, 4);
}
```

`gen_guid()` 的签名要求 `unsigned char[16]`，却传入了 4 字节的数组，
造成 12 字节栈越界写。该分支在 `disk_signature == 0` 时必然执行，
而 CLI 默认就是 0——也就是说**默认路径一直在越界**。已改为 `r[16]`。

### 6.4.2　`detect_system_disks()` 的 mountinfo 解析错误

```c
/* 修复前 */
mp = strstr(line, " / ");          /* 猜挂载点位置 */
```

`/proc/self/mountinfo` 的字段是
`id parent major:minor root mount-point options ...`——
`root` 字段也在挂载点之前，所以 `strstr(line, " / ")` 命中的是 **root 字段**。

- 对根文件系统（root = `/`）恰好正确；
- 对 `ntfs-3g` 这类 **FUSE** 挂载（root = `/`，挂载点在 `/mnt/nt`），
  会把 `/dev/loop0p1` 误判为"承载 `/` 的系统盘"，
  从而**拒绝操作一个完全无关的 U 盘**。

已改为按字段解析（`sscanf("%*d %*d %u:%u %4095s %4095s", ...)`），
并把分区名的上跳判定改为"以整盘名为前缀且更长"。

### 6.4.3　JSON 解析器的双重编码

`rf_json.c` 的字符串解析对**非转义字节**误用了 `utf8_put()`：

```c
/* 修复前：把每个字节当成一个 Latin-1 码点，再 UTF-8 编码一次 */
cp = (unsigned char)*ps->p++;
len += utf8_put(out + len, cp);
```

输入本身已是 UTF-8，这样会把 `评`（`E8 AF 84`）变成 `è¯\x84`
（`C3 A8 C2 AF C2 84`）——即双重编码。表现为目录里的中文名显示为乱码。

修复：非转义字节**原样复制**，只有 `\uXXXX` 转义才走 `utf8_put()`。
单元测试确认「原文 UTF-8」与「`\u` 转义」两种写法解析结果逐字节一致，
代理对（emoji）也正确。

### 6.4.4　冲突检测的两处误报

初版 `path_matches_any()` 的前缀匹配写成了：

```c
/* 修复前 */
if (strncmp(p, t, n) == 0 && (p[n] == '/' || (t[n - 1] == '/')))
    return 1;
```

当 `t` 是根挂载点 `"/"`（`n == 1`）时，`t[n-1] == '/'` 恒为真，
于是**任何绝对路径都会命中**：`rufus ps /dev/sda` 一次报出 183 个
"占用者"，连 `/dev/null` 和 `cwd=/home/builder` 都被算进去。

修复分两步：

1. 前缀匹配必须落在路径分量边界上（`p[n] == '/'`），并排除 `n <= 1`；
2. 目标路径集合中**不再加入根挂载点 `"/"`**——"cwd 是 `/`" 对所有
   守护进程都成立，对"谁占用了这块 U 盘"毫无信息量，而承载 `/` 的
   设备本来就会被系统盘检查拒绝。

修复后 `/dev/sda` 只报出真实占用（交换分区 `/dev/sda3`），
`/dev/loop0` 精确报出 2 个 `sleep` 进程。

### 6.4.5　顺带统一的设备节点识别

1.0.0 版在多处用 `isdigit(dev[strlen(base)])` 判断分区节点，
无法识别 `loop0p1` / `nvme0n1p1` / `mmcblk0p1` 这类带 `p` 分隔符的命名——
这会导致回环设备与 NVMe 的**分区不被列出**，进而
"卸载设备上的所有分区"失效。现统一为公共函数：

```c
int rf_dev_is_partition_of(const char *path, const char *base);
/* /dev/sdb1、/dev/loop0p1、/dev/nvme0n1p1、/dev/mmcblk0p1 都返回 1 */
```

## 6.5　测试结论

三项功能的实机测试结果见第 5 章测试 13–17：

| 功能 | 验证方式 | 结果 |
| --- | --- | --- |
| 冲突进程检测 | 制造 3 个真实占用者（挂载进程 + 打开文件 + cwd） | ✅ 全部识别，分类正确 |
| 冲突拦截 | 有冲突时 `create` 被拒绝；`--no-conflict-check` 强行继续后 `cp` 确实失败 | ✅ 证明拦截必要 |
| 在线下载 | 真实 HTTPS 下载 + 官方 SHA256 校验；正例与反例 | ✅ 通过 |
| 目录真实性 | 独立抽查 4 个 URL，`Content-Length` 与目录 `size_bytes` 完全一致 | ✅ 通过 |
| 校验和格式 | Fedora BSD 风格 / Ubuntu `*` 标记 / 带路径前缀 / 裸 hash / 反例 | ✅ 全部正确 |
| UEFI:NTFS | GPT 双分区 + `sgdisk -v` 无问题 + 属性位 63 + 分区内容为完整 UEFI:NTFS 驱动 | ✅ 通过 |
